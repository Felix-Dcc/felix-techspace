class OrderService:
    """Single source of truth for order state."""

    def transition(self, order, to, actor):
        if to not in ALLOWED[order.status]:
            raise IllegalTransition(order.status, to)
        if actor.role not in OWNERS[to]:
            raise PermissionDenied(actor, to)

        with transaction.atomic():
            order.status = to
            order.save(update_fields=["status"])
            History.objects.create(order=order, status=to)
            notify.delay(order.id, to)   # celery
        return order

What it does

A customer books a laundry pickup. A rider is dispatched, collects the load and delivers it to a laundromat. The provider weighs it, the customer pays the verified amount, and the clean laundry is routed back — every step tracked live, every transition audited.

Four different people see four different applications, all reading from one API and one order record.

Technical decisions

One state machine, no exceptions

Order status lives in exactly one place: a pure module of data and side-effect-free functions listing every legal transition and the role allowed to make it. The service layer executes; clients render but never decide. Client/server state divergence stops being a bug you fix and becomes a state you cannot express.

Compute, don't store

Riders hold several concurrent pickups. Rather than maintaining a counter that can drift, the active-task count is derived on read from order status. There is no second copy of the truth to fall out of sync.

Payment-gated work

Washing cannot start until a provider-verified weight has been recorded and paid for. The gate lives in the transition rules, not in UI validation, so no client can skip it.

A dependency you don't need is a risk

Signed direct-to-CDN image uploads are implemented with the standard library's crypto primitives instead of the vendor SDK, keeping the container build reproducible against a committed lockfile.

Problems solved

  1. Two releases shipped broken to testers

    Symptom: every sign-up failed with "cannot reach server." Cause: optional chaining in the build config silently defeated compile-time environment inlining, so the production API URL never made it into the Android bundle. Fix: corrected the config, then added a pre-upload gate that unpacks the built artifact and asserts the production URL is present before anything reaches the store.

  2. ~400 device models silently excluded

    An auto-generated manifest was declaring a camera permission the app never used, which the store treats as a hardware requirement. Auditing and removing it restored availability to roughly 400 additional Android devices.

  3. Admins seeing stale data after deploys

    The dashboard served a cached HTML entry point pointing at expired asset hashes. Fixed by making the entry point no-cache while keeping content-hashed assets immutable.

About

I build the part users never see

Most of what makes software feel trustworthy happens behind the interface: the request that fails cleanly instead of half-succeeding, the permission check that can't be skipped, the migration that runs at 2 a.m. without waking anyone. That's the work I want.

I build APIs and services in Python — Django and DRF when a project needs a full framework and an admin surface, FastAPI when it needs to be lean and fast — backed by PostgreSQL, with Redis for caching and Celery for anything that shouldn't block a response. I containerise with Docker and put changes behind CI so mistakes surface before users find them.

My approach is to make bad states unrepresentable rather than merely unlikely. On LaundroMart, that meant one state machine owning every order transition instead of status writes scattered across routes, and deriving values on read rather than storing counters that drift. Fewer places to be wrong beats more tests over a fragile design.

I also care about the operational side — structured logs, metrics, audit trails, sensible rate limits — because a service you can't observe is a service you can't actually run. And I'm still early enough in my career to be genuinely eager for code review from people further along.

  • Correctness first. Then performance. Then cleverness, if ever.
  • Boring infrastructure. Surprises belong in the product, not the deploy.
  • Own the whole path. Schema to production, including the parts that break.
